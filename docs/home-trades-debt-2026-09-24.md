## 2. Backend (Supabase) — prepared migration; deployment pending
- [ ] Trades H2(e): exactly-once collection application across devices/reinstalls. A remote
      `collection_applied_at` read before Room apply and write afterward is unsafe: concurrent
      devices can both apply, and a claim lease cannot distinguish a crash before local commit
      from one after it. This needs an authoritative server operation ledger, changes to
      `batch_upsert_collection` snapshot/LWW behavior, SyncManager push/pull reconciliation, and
      compatibility for released clients. The unsafe marker was removed from SQL and Kotlin;
      the per-installation Room gate remains. **Trades-specific debt, not closed.**
- [ ] Trades H4: reject `revoke_acceptance` once either party has marked completed.
- [ ] Trades H5: RLS on trade proposals lets the receiver read DRAFT rows (client "Save draft" was
      removed; legacy drafts render without actions).
- [ ] Trades M13: `create_proposal`/`counter_proposal` idempotency key (`p_client_request_id`),
      `SELECT … FOR UPDATE` in state RPCs, `IF NOT FOUND` on unknown ids.
- [ ] Trades M14: server-side validation that a referenced collection row belongs to the sender and
      matches the card.
- [ ] `resolve_shared_list` returns wishlist items without `quantity` (always ×1) and its "private"
      status only checks the owner still exists (no real sharing flag).
- [x] The five paginated gamification `get_*_page` RPCs were deployed on 2026-09-25; the old
      `*_changes_since` RPCs remain for released clients.

The H4/H5/M13/M14/shared-list SQL changes above are implemented in the migration but remain
unchecked until deployment and verification. The active database has seven historical invalid
collection references, including three PROPOSED trades; acceptance now revalidates them under
lock. Deployment must precede enabling calls to the new idempotency signatures.
